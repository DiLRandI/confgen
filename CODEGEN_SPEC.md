# Code Generation Specification

## 1. Purpose

`configgen` converts a validated schema into deterministic Go code and optional examples.

Input:

```text
config.schema.yaml
```

Primary output:

```text
config_gen.go
```

Optional outputs:

```text
config.example.yaml
.env.example
```

## 2. CLI

Minimum supported invocation:

```bash
configgen -schema config.schema.yaml -out config_gen.go
```

Recommended `go:generate` usage:

```go
//go:generate go run github.com/ORG/PROJECT/cmd/configgen -schema config.schema.yaml -out config_gen.go
```

Optional flags:

```text
-schema <path>          required schema file
-out <path>             generated Go output
-example-yaml <path>    optional YAML example output
-example-env <path>     optional env example output
```

The final module path is repository-owner-controlled and should not be hardcoded until the repository name is chosen.

## 3. Generation stages

1. Read schema bytes.
2. Parse YAML with duplicate-key detection.
3. Validate schema semantics.
4. Build normalized schema IR.
5. Generate Go source.
6. Run `go/format`.
7. Generate optional examples.
8. Write all requested outputs atomically.

If any requested output cannot be generated, no previously existing target should be corrupted or partially replaced.

## 4. Generated header

Every generated Go file begins with:

```go
// Code generated by configgen. DO NOT EDIT.
```

Do not include timestamps, hostnames, absolute schema paths, or other nondeterministic content.

## 5. Generated types

For schema:

```yaml
fields:
  server:
    type: object
    fields:
      host:
        type: string
      port:
        type: int
```

prefer:

```go
type Config struct {
    Server ServerConfig `json:"server" yaml:"server"`
}

type ServerConfig struct {
    Host string `json:"host" yaml:"host"`
    Port int    `json:"port" yaml:"port"`
}
```

Nested object type names are deterministic from the owning path. If collisions occur, generation fails rather than silently renaming unpredictably.

## 6. Struct tags

Generate JSON and YAML tags using the original schema key:

```go
Port int `json:"port" yaml:"port"`
```

Tags are convenience metadata for user code; they are not the runtime schema authority.

## 7. Generated descriptor

Generate immutable descriptor metadata containing all runtime-relevant information:

- canonical path;
- field kind;
- Go assignment location/index;
- required;
- default presence and value;
- secret flag;
- env mapping or disabled state;
- constraints;
- child/item/value descriptors as needed.

The descriptor should be package-private in generated code unless a public exposure has a concrete use case.

## 8. Generated helper functions

Generate:

```go
func Load(sources ...config.Source) (*Config, error) {
    return LoadContext(context.Background(), sources...)
}

func LoadContext(ctx context.Context, sources ...config.Source) (*Config, error) {
    return config.Load[Config](ctx, descriptor, sources...)
}

func MustLoad(sources ...config.Source) *Config {
    cfg, err := Load(sources...)
    if err != nil {
        panic(err)
    }
    return cfg
}
```

Exact runtime import aliasing must avoid collisions with generated package identifiers.

## 9. Imports

Only import packages actually required by generated code. Typical imports:

```go
context
time
<runtime package>
```

No unused imports may be generated.

## 10. Stable ordering

Preserve schema field order in generated structs, descriptors, and examples.

Where maps are generated internally, sort keys before rendering.

Two runs against identical input and generator version must produce byte-identical formatted outputs.

## 11. Atomic writes

Generate into memory first. Write to a temporary file in the destination directory, sync/close appropriately, then rename over the target.

Generation failure must leave the previous output intact.

## 12. Example YAML generation

When requested, generate a readable configuration template in schema order.

Recommended rules:

- defaulted fields show defaults;
- required fields without defaults show a neutral placeholder compatible with the field type;
- descriptions may be rendered as comments;
- nested objects are emitted structurally;
- secrets never receive realistic secret-looking example data;
- lists/maps use empty or schema-default values.

Example:

```yaml
server:
  host: 0.0.0.0
  port: 8080
  timeout: 30s

database:
  url: ""

storage_dir: ./data
debug: false
```

## 13. Environment example generation

When requested, emit enabled env mappings in schema order.

```dotenv
APP_SERVER_HOST=0.0.0.0
APP_SERVER_PORT=8080
APP_SERVER_TIMEOUT=30s
DATABASE_URL=
APP_STORAGE_DIR=./data
APP_DEBUG=false
```

For list/map values, use JSON syntax. Secret fields without safe defaults emit an empty value.

## 14. Schema validation belongs before rendering

Rendering code should assume the schema IR is valid. Do not duplicate semantic validation across templates.

## 15. Generator error behavior

CLI errors must:

- print to stderr;
- include schema path/location when possible;
- exit non-zero;
- avoid Go panic traces for ordinary schema mistakes.

## 16. Compilation acceptance

Generated output must compile in a temporary test module against the runtime package. Add an integration test that generates source from a fixture schema and runs `go test` on the fixture package.

## 17. Determinism acceptance

Test generation twice from identical bytes and compare outputs byte-for-byte.

## 18. Future-compatible design

Keep schema normalization separate from Go rendering so future generators can produce JSON Schema, docs, or alternate language artifacts without reparsing schema logic.
